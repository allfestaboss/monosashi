# monosashi.work — 物差し（AI実務到達度インデックスの公開サイト）

[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.22002590.svg)](https://doi.org/10.5281/zenodo.22002590)

https://monosashi.work

職種ごとに、AIが実務をどこまでやれるかを同じ物差しで実測して公開する
[AI実務到達度インデックス](https://doi.org/10.5281/zenodo.21862231) の公開面。
各業種の測定そのものは別リポジトリにあり、このリポジトリはサイトの生成だけを持つ。

```
site/<職種>/body.html   記事の本文（Artifact と同一。**書き直さない**）
site/<職種>/reviewed.json  その記事がベンチのどの版に対応するか
build.py                外枠をかぶせて dist/ を作る
deploy.sh               dist/ を VPS に転送してコンテナを差し替える
```

## 撤回をどう出しているか

ベンチは版を出し続け、ときに結果を撤回する。サイトがそれを写して持つと
**同じ文が2箇所に存在して片方が腐る**ので、**このリポジトリには撤回文を1文字も置かない。**

- 正本は各ベンチの `.zenodo.json`（撤回文）と `CITATION.cff`（版・DOI）
- 規約は「`<p>` の本文が `Version X.Y.Z` で始まる段落＝その版の変更記録」。9リポで較正済み
- `build.py` が読んで、記事の対応版と現行版を突き合わせる
  - 一致 → 1行の注記
  - 不一致 → 間の版の段落を**そのまま**差し込む（要約すると二重管理が復活する）
- [/changes/](https://monosashi.work/changes/) は全ベンチ横断の台帳。**掲載していない業種も載せる**

`reviewed.json` は2欄を別に持つ。混ぜると「版差を開示したままデプロイする」が表現できない。

| 欄 | 意味 | 性質 |
|---|---|---|
| `version` | 本文がどの版に対応するか | 事実。読者に見せる |
| `acknowledged` | 人がどの版まで読んで判断したか | 判断。関門の根拠 |

## 検査

```bash
python3 build.py           # 生成。acknowledged が現行版より古ければ終了コード 1
python3 build.py --check   # 書かずに版のドリフトだけ見る（日次ジョブから毎晩）
```

関門が build を落とさず終了コードだけ返すのは、**差し込まれた内容を見てから
確認印を打てるようにする**ため。build ごと落とすと、確認するために確認印を打つ
という順序の逆転が起きる。

`--check` を毎晩走らせているのは、build の関門が**デプロイしない期間のドリフトに
無力**だから。実際 2026-08-10〜12 にベンチ5本が新版を出したがサイトは誰も触らず、
関門は一度も鳴らなかった。
